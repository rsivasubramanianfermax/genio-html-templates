ME Platform (Doors & Lifts)

Relay-based door & lift access via WebSocket — beacon unlock, floor-aware lifts, time zones

Overview

What is the ME (Micro Engine) Platform?

The ME Platform — short for Micro Engine — is iplus's integration with physical door and lift (elevator) access controllers. Unlike the Fermax Meet/MQTT module (which is built around video intercom panels with on-device facial recognition), the ME platform is a door/lift relay control system: each physical door or lift controller is registered with a controller_code, and access is granted by sending an unlock/floor-call instruction to that controller in real time.

🔌

WebSocket is the transport

When a resident requests door/lift access, iplus sends a JSON instruction to a WebSocket gateway, which forwards it to the physical controller identified by controller_code.

📶

Beacon (BLE/NFC) proximity unlock

Doors and lifts can optionally be configured with a beacon_uuid and detection range — the resident's phone detects the beacon and can trigger access automatically when nearby.

🛗

Lifts are floor-aware

Lift access isn't just "call the lift" — each unit is mapped to specific accessible floors via lift buttons, so a resident's app only shows the floors they're permitted to reach.

⏰

Time zones & holidays

Every door/lift access grant (resident or staff) is checked against a configured time zone (schedule) and holiday calendar before access is allowed.

Actors

Who is Involved? (ME Platform)

🚪

ME Door Controller (Hardware)

Physical access controller wired to a door lock/gate. Identified by controller_code + door_code; receives unlock instructions via the WebSocket gateway.

🛗

ME Lift Controller (Hardware)

Controller wired to an elevator's floor-selection panel. Identified by controller_code + lift_code; each floor is a "lift button" (floor_access_code).

🌐

WebSocket Gateway

Middleware service (virtual_button_socket_url) that receives JSON access requests from iplus and relays them to the physical ME controller hardware.

🏠

Resident

Sees accessible doors/lifts (and permitted floors) in the app under "Virtual Buttons" — taps to unlock a door or call a lift to a floor.

🛡️

Staff

Granted access to door/lift groups via staff access groups + role mappings, scoped by time zone (e.g. cleaners only during working hours).

🏢

Property Management

Registers doors/lifts (incl. bulk CSV import), defines groups, time zones, holidays, and unit/staff access mappings via the backend.

End-to-End Flow

How Access is Configured & Triggered — Step by Step

1
Doors and lifts are registered in iplus
Property management registers each physical door/lift controller against the condo, one-by-one or via bulk CSV import.
Backend: backend/controllers/MeDoorController.php (doors), MeLiftsController.php (lifts)
Tables: me_doors, me_lifts — store controller_code (hardware ID), door_code / lift_code (relay/access code), name, status
Optional: beacon_uuid, beacon_min_range, beacon_max_range, is_beacon_enabled
2
Lift floor buttons are configured
For each lift, the floors it serves are defined as individual "lift buttons" so the app can show floor-level access.
Table: me_lift_button — floor_access_code, lift_button_name (e.g. "Ground Floor"), sort_order
Grouping: me_lift_button_group + me_lift_button_group_button_link — groups of floor buttons for staff/visitor scoping
me_lift_floor_mapping — links lifts to physical condo floors
3
Doors/lifts are organised into groups
Individual doors and lift button groups are organised into logical groups for easier permission management.
me_door_group + me_door_group_door_link — groups of doors
me_lift_group + me_lift_group_lift_link — groups of lifts
me_amenity_mapping — links amenities to lift button groups (e.g. lift access to a gym floor)
4
Time zones & holidays are defined
Access windows are defined once and reused across door/lift/group mappings.
me_time_zones — named schedules (e.g. "24/7", "Office Hours")
me_time_intervals + me_time_zone_interval_link — specific day/time ranges linked to a time zone
me_holidays — holiday calendar, excluded from normal schedules
5
Units are mapped to doors, lifts & floors
Each unit (resident) is granted access to specific doors, lifts, and — for lifts — specific floors, each tied to a time zone.
me_unit_mapping — master link: unit → group_id + type (1=door, 2=lift) + me_time_zone_id
me_unit_door_mapping — unit → specific door (door details copied at mapping time for fast lookup)
me_unit_lift_mapping — unit → specific lift, with its own is_beacon_enabled flag
me_unit_lift_floor_mapping — unit → lift → specific accessible floors
6
Staff access groups are configured
Staff (cleaners, technicians, security) are granted recurring access to door/lift groups, scoped by time zone — separate from resident unit mappings.
me_staff_access_group — staff group definitions
me_staff_role_mapping — links a staff role to a door group or lift button group, type = 1 (door) / 2 (lift)
7
Cross-module unification (optional)
ME door/lift groups can be linked into iplus's unified access-group abstraction, alongside other access hardware (Hikvision FR, Meet FR, virtual buttons).
common_access_group — umbrella group ("Micro Engine Access Group" label for ME)
common_access_group_mapping — type = 1 for ME doors, type = 2 for ME lifts (staff)
Backend: CommonAccessGroupController.php
8
App shows accessible doors & lifts ("Virtual Buttons")
The resident/staff app fetches the list of doors and lifts they can currently access, filtered by their unit/role and the active time zone.
API: POST /apiver6/virtual-buttons/doorslist
For lifts, a follow-up call returns the floors available right now:
API: POST /apiver6/virtual-buttons/accesiblefloorlist (param: unit_door_mapping_id)
Logic: Apiver3::getAccessibleDoorsAndLifts() — checks unit/staff mapping + time zone/holiday rules
9
Resident taps "Open Door" / calls a lift
The action is validated server-side, logged, then sent in real time to the WebSocket gateway, which forwards it to the physical controller.
API: POST /apiver6/virtual-buttons/dooraction (params: unit_door_mapping_id, type 1=door / 2=lift)
1. Re-validate permission (mapping + time zone)
2. Insert into me_access_log (status=1 pending) → returns sync_ack_id
3. Send JSON over WebSocket: controllername (controller_code), doorcode/floor info, sync_ack_id, unit/user details, beacon & time-zone settings — plus the security/energy fields described in Part 2
4. Fallback: if WebSocket send fails, retries via virtual_button_socket_open_url (HTTP)
10
Hardware actuates & result is logged
The physical ME controller unlocks the door / sends the floor-call signal, then the access attempt's outcome is recorded for audit.
me_access_log — updated to status = 2 (success) or status = 3 (failure)
History API: POST /apiver6/virtual-buttons/accessloglist
11
Beacon-based hands-free access (alternative path)
If beacon access is enabled on a door/lift, the resident's phone detects the configured BLE/NFC beacon and can trigger the same unlock flow without manually opening the app.
Door/lift fields: beacon_uuid, beacon_min_range, beacon_max_range, is_beacon_enabled
Validation: beacon UUID match + resident within configured range + permission + time zone all pass before access is granted

Facility Security & Energy Control

Hotel-card-style relay control for security arm/disarm and power/AC, layered on the ME Platform's dooraction flow

Overview

What is Facility Security & Energy Control?

Facility Security & Energy Control is a configuration layer on top of the ME Platform (Part 1) that mimics the classic hotel room key-card experience: when a resident's credential is scanned/used at a door, the system can also instruct a relay to arm/disarm a security zone and/or switch on/off power, lighting, or AC for that room/amenity.

It is configured per amenity (facility/room) and gated by two condo-level feature flags. The resulting settings are bundled into the same WebSocket payload that the ME Platform sends for door/lift actions — there is no separate hardware protocol; it rides on the existing dooraction flow described in Part 1, Step 9.

🔐

Security On/Off

An amenity/room can have a "security" relay tied to one or more door codes — e.g. arming an alarm zone when the door is locked, disarming when accessed.

⚡

Energy On/Off

A separate "energy" relay (named via me_output_name) controls power/AC/lighting for the room — classic "insert card to turn on power" behaviour.

🔁

Operation modes

Each relay can be: Disabled, Activate/Release on First Scan (one-shot), or Toggle (every scan flips state).

⏳

Grace periods & reminders

A grace period (minutes) delays the energy cutoff after the door closes, with an optional reminder notification before power is cut.

⚠ Implementation Status

This feature is configured end-to-end but only partially wired. The amenity table columns and the backend admin form (backend/views/amenity/_form.php) are fully built, and the fields are included in the dooraction WebSocket payload sent to the ME Platform gateway. However, common/models/Apiver3.php (which builds the doors/lifts list) currently defaults all security/energy fields to 0 (disabled) rather than reading them from the amenity table — so in practice, the relay instructions reaching the gateway are inert until that lookup is implemented. Treat this as a "schema + UI ready, runtime wiring incomplete" feature.

Actors

Who is Involved? (Security/Energy)

🏢

Property Management

Enables the security/energy feature flags at condo level (condo_setting), then configures per-amenity behaviour (mode, door codes, grace periods, output names).

🛗

ME Platform Gateway

Same WebSocket gateway used for door/lift unlock (Part 1) — receives the security/energy fields alongside the door/lift command and is expected to drive the physical relays.

🔌

Relay / Output Hardware

Physical relay board wired to room power, AC contactor, lighting circuit, or alarm panel — addressed via me_output_name and door codes (me_door_code / me_energy_door_code).

🏠

Resident

Triggers the behaviour indirectly — by performing a normal door/lift action (or beacon scan) on a door whose amenity has security/energy enabled.

🔔

Reminder Recipient

Receives the configurable "energy cutoff reminder" notification (me_energy_cutoff_reminder_notification_text) before power is switched off after the grace period.

📋

Audit Log

me_access_log records the underlying door/lift action that carried the security/energy instruction — there's no separate energy-specific log table.

End-to-End Flow

How It's Configured & Triggered — Step by Step

1
Condo-level feature flags are enabled
Before any amenity can use security/energy control, the condo must have the relevant feature switched on.
Table: condo_setting
me_door_security_on_off_feature — enables the Security section in the amenity form
me_energy_on_off_feature — enables the Energy section in the amenity form
File: backend/models/Condosetting.php
2
Security behaviour is configured per amenity
For a facility/room, management defines whether entering arms/disarms a security relay, and how.
Table: amenity — fields:
me_security_on_off (0/1 enable)
me_security_operation_mode — 0=Disable, 1=Release on First Scan, 2=Toggle
me_door_code — comma-separated door codes this relay applies to
me_security_grace_period — minutes before re-arming
UI: backend/views/amenity/_form.php (lines ~177-239)
3
Energy behaviour is configured per amenity
Similarly, management defines whether entering switches on power/AC/lighting, and the cutoff behaviour after leaving.
Table: amenity — fields:
me_energy_on_off (0/1 enable)
me_energy_operation_mode — 0=Disable, 1=Activate On First Scan, 2=Toggle
me_energy_door_code — door codes for the energy relay
me_output_name — name/identifier of the relay output (power/AC/lighting circuit)
me_energy_grace_period — minutes of delay before cutoff after door closes
me_energy_cutoff_reminder_notification_text / _time — pre-cutoff reminder
UI: backend/views/amenity/_form.php (lines ~240-298)
4
Resident performs a door/lift action
No separate "security/energy" UI exists for residents — the trigger is simply using the door/lift as normal (app tap or beacon scan), as described in Part 1, Steps 8-9.
API: POST /apiver6/virtual-buttons/dooraction
File: apiver6/controllers/VirtualButtonsController.php:342-572
5
Security/energy fields are bundled into the WebSocket payload
Alongside the door/lift unlock command, the same JSON payload carries the relay configuration for that door.
File: apiver6/controllers/VirtualButtonsController.php:463-499
Payload fields: me_security_on_off, me_security_operation_mode, me_security_grace_period, me_door_code, me_energy_on_off, me_energy_operation_mode, me_energy_grace_period, me_energy_door_code, me_output_name
6
⚠ Gap: values are not yet sourced from the amenity table
The query layer that builds the doors/lifts list does not currently join to amenity for these fields.
File: common/models/Apiver3.php (getAccessibleDoorsAndLifts() and related, ~lines 2287-2640, 2845-3400)
Current behavior: me_security_on_off, me_energy_on_off, etc. are hardcoded to 0 (disabled) in the response/payload construction
7
ME Platform gateway executes the relay action (intended)
Once wired, the WebSocket gateway / physical ME controller would interpret the security/energy fields and drive the corresponding relay output.
Operation mode 1 (Release/Activate on First Scan) → one-shot relay trigger on first valid access
Operation mode 2 (Toggle) → relay flips state on every valid access
Grace period → gateway/hardware delays de-energizing by me_energy_grace_period minutes after door closes
8
Reminder notification before energy cutoff (intended)
If a grace period is configured, a reminder can be sent shortly before the relay de-energizes the room.
Fields: me_energy_cutoff_reminder_notification_time (minutes before cutoff), me_energy_cutoff_reminder_notification_text (message template)
No dedicated scheduler/cron for this was found — likely intended to be driven by the ME gateway or a future job

Audit Trail & Notifications

Logging & Visibility

📋

Every Access Attempt is Logged

me_access_log records company/condo, user, unit, location (door/lift), type, timestamp, and final status (pending → success/failure) — queried via accessloglist for the resident's access history. This same record is the only audit trail for any security/energy action that rode along with it.

✅

Real-Time Success/Failure

The app receives a synchronous response to dooraction reflecting whether the WebSocket gateway successfully relayed the command to the controller.

🔄

Cache Invalidation on Config Change

When access groups / mappings change in the backend, CommonComponent invalidates cached access-group data so the app's "doorslist" reflects updates immediately.

🔔

Resident — Power/AC About to Be Cut (Part 2, intended)

If me_energy_grace_period and me_energy_cutoff_reminder_notification_time are configured, a reminder using me_energy_cutoff_reminder_notification_text is intended to be sent before the relay de-energizes the room. No dedicated scheduler/cron job for this was found in the codebase — the trigger mechanism is not yet implemented.

Security

Security & Access Control Features

Time-Bound Access

Every door/lift mapping (resident or staff) is checked against a configured time zone and holiday calendar before the unlock command is sent.

Floor-Level Lift Permissions

Lift access is not all-or-nothing — me_unit_lift_floor_mapping restricts which floors a unit can select, even within an accessible lift.

Unified Access Groups

common_access_group lets a single access policy span ME doors/lifts alongside Hikvision FR, Meet FR, and virtual buttons — consistent permissions across systems.

Beacon Range Validation

Beacon-enabled doors/lifts validate both UUID match and proximity (beacon_min_range/beacon_max_range) before granting hands-free access.

Same Transport, No New Protocol

Security/energy fields are appended to the exact same WebSocket payload used for door/lift unlock (dooraction) — there is no separate MQTT topic, REST endpoint, or polling mechanism for this feature.

Currently Inert (Security/Energy)

Until Apiver3::getAccessibleDoorsAndLifts() is updated to read security/energy fields from amenity instead of defaulting to 0, no real relay commands will be triggered — a key gap for Genio360 to close (or redesign) if this feature is in scope.

Summary

How the Two Parts Fit Together

One Trigger, Two Outcomes

A single resident action — tapping "Open Door" or a beacon-triggered scan — can simultaneously (a) unlock the door/lift (Part 1, fully functional) and (b) carry security/energy relay instructions (Part 2, configured but not yet read from amenity).

Configured at Different Levels

Part 1 access permissions are configured per unit/staff mapping; Part 2 security/energy behaviour is configured per amenity and linked back to doors via door codes.

Genio360 Consideration

If hotel-style "card activates room power" is a target feature for Genio360, the Part 2 schema is a reasonable starting reference — but the actual relay protocol (what the ME gateway expects, and how it confirms success) was not found in this codebase and would need to be sourced from the ME hardware vendor's documentation. The Part 1 door/lift flow can be used as-is as the reference architecture for relay-based access.
