Super Admin Backend
Business Process Guide

This document describes what happens functionally when a Super Admin or Property Manager uses the iPlus Living backend — covering every actor, every decision, every outcome, and every business rule in plain language.

Audience: Business Analysts, Product Managers, QA, Onboarding Teams System: iPlus Living Backend Panel Prepared by: Sivasubramanian R

1 Actors — Who Does What

The backend panel has two types of actors. Understanding who acts at each stage is critical to understanding the functional flows.

Super Admin

  • Belongs to iPlus Living (the platform provider)
  • Creates and manages all condos across all companies
  • Creates Property Manager accounts and assigns them to condos
  • Sets up roles, permissions, and global settings
  • Manages subscription and licensing for each condo
  • Can access every condo, every feature, every report
  • Highest level of trust in the system

Property Manager (PM)

  • Belongs to the property management company
  • Can only see and manage their assigned condos
  • Creates and manages staff, concierge, resident accounts within their condos
  • Configures day-to-day condo settings
  • Cannot create new condos or touch other companies' data
  • Cannot manage roles globally — only assigns existing roles

Supporting Actors (outside the backend panel)

  • Staff / Concierge — Use the frontend portal. Created by PM/Super Admin in backend but never log into the backend panel itself.
  • Resident — Use the mobile app / resident portal only. Created by PM or self-register. No backend access.
  • System — Automated actions triggered by the platform (cache clearing, sync, notifications) that happen without a human initiating them.

2 End-to-End Onboarding Journey

When a new property joins iPlus Living, this is the complete journey from zero to residents using the app — in the order it must happen:

Phase 1 — Property SetupSuper Admin
  • Super Admin creates the condo record with name, address, package, currency, timezone
  • Super Admin sets condo status — "Under Construction" or "Active"
  • Super Admin configures 100+ condo settings (payment gateway, language, booking rules)
  • Super Admin sets up module branding (custom names for modules and roles)
Phase 2 — Structure SetupSuper Admin
  • Define blocks/towers → floors → units (can be done manually or via CSV import)
  • Map units to physical access controllers (door, lift)
  • Import QR codes for units (for key collection and visitor access)
Phase 3 — Role & Permission SetupSuper Admin
  • Create roles if custom roles are needed (e.g., "Security Guard" as a sub-type of Staff)
  • Assign roles to the condo (activate them for this property)
  • Set module permissions for each role — what each role can View, Add, Update, Delete, Approve
  • Configure tenancy agreement if residents must accept house rules on first login
Phase 4 — User OnboardingSuper Admin + PM
  • Super Admin creates the Property Manager account and assigns to the condo
  • PM (or Super Admin) creates staff and concierge accounts
  • Residents self-register via mobile app using their unit number, OR PM bulk-imports resident data
  • If it is a construction-phase condo: developer and contractor accounts are created first
Phase 5 — Go LiveSuper Admin
  • Super Admin confirms condo status is "Active"
  • If was under construction: mark as construction-completed → developer access reduced, resident features enabled
  • Residents can now download the app, register, and start using all features
  • PM monitors day-to-day operations through the frontend portal

4 Functional Flow: New Property Onboarding

Super Admin

Super Admin receives a new property onboarding request

The property management company has signed up with iPlus Living. The Super Admin is given the property details — name, address, number of units, blocks, floors, preferred currency, and subscription package.

Create the condo record

Super Admin opens the Condo section in the backend panel and clicks Create. They fill in: property name, full address, number of blocks, number of floors, number of units, currency (e.g. SGD), timezone (e.g. Asia/Singapore), and assigns a subscription package. The subscription start and end dates define when the condo's licence is valid.

Set the condo status

If the building is occupied and ready to go live: set status to Active. If the building is still under construction: set status to "Under Construction" — this enables developer and contractor access while keeping resident features hidden.

Upload condo branding

Upload the condo logo and configure home screen banner images that residents will see when they open the app. These are condo-specific — each property has its own visual identity.

Configure all condo settings

Go to Condo Settings and configure the 100+ behaviour flags. The critical ones at this stage are: default language, payment gateway, password policy, booking auto-approval toggle, and any module name customisations. Settings can be changed later — they do not need to be perfect at creation time.

Assign roles to the condo

Go to Condo Roles and link the global role definitions to this condo (e.g., activate "Staff", "Concierge Admin", "Resident" for this property). Only activated roles can be assigned to users of this condo.

Set permissions for each role

For each role activated in this condo, define exactly which modules they can access and what they can do within each module. For example: Concierge can View and Add visitors, but cannot Delete or Approve facility bookings.

Create the Property Manager account

Create the PM user account with name, email, and temporary password. Assign role_group = 5 (Property Manager). Link the PM to this condo. The PM receives login credentials and can now access the backend for their assigned condos only.

Hand over to the Property Manager

The PM now handles the remaining setup: importing units, creating staff accounts, and guiding residents through registration. Super Admin's onboarding work is complete for this property.

5 Functional Flow: Setting Up Units & Blocks

Super AdminProperty Manager
Why this matters: Every resident, parking spot, booking, visitor, and service request is linked to a specific unit. Units must be set up correctly before any user can be assigned or any resident feature can work.

Decide: manual entry or CSV import

For small properties (under 50 units), admin may enter units manually. For large properties, CSV import is the standard approach. A blank CSV template can be downloaded from the backend.

Set up blocks (towers)

Create each residential block or tower by name (e.g., "Tower A", "Block 3"). Each block gets a sort order for display. Carpark blocks are created separately if needed.

Define units under each block

For each block: create units with unit name (e.g., "01-01"), floor number, and unit type. Unit types: Residential (standard apartment), Commercial (shop lot), Carpark (parking bay).

Map units to access controllers

If the property has smart access (lift, door controllers): link each unit to the relevant controller zones. This determines which floors and doors a resident can access based on their unit. This mapping is done via the Access Mapping action.

Import purchase / owner data (optional)

For new-launch properties: import the purchase price, buyer name, and ownership details per unit. This is used for key collection tracking and developer handover management.

Generate QR codes for units (optional)

QR codes can be generated and printed for each unit. Used for: key collection confirmation scanning, visitor pre-registration by residents, and physical access at certain condos.

Important: Unit names must match exactly what residents know their unit as (e.g., "#01-01" vs "01-01" vs "0101"). Mismatches cause registration failures when residents try to self-register using their unit number.

6 Functional Flow: Construction Mode → Going Live

Super Admin

While "Under Construction"

  • Resident-facing features are hidden / disabled
  • Developer (role_group=11) and contractor accounts have elevated access to: defect inspection checklists, key collection management, floor plan uploads, unit handover tracking
  • Residents can be pre-registered but cannot fully access the app
  • Property Manager can still configure the condo during this phase

When "Mark as Completed"

  • Super Admin clicks "Mark Construction as Completed" for the condo
  • Condo status changes to Active
  • Developer access is automatically reduced to view-only or removed
  • All resident-facing features activate: bookings, visitors, community wall, parcels, etc.
  • Residents who pre-registered can now fully use the app
  • This action is irreversible without Super Admin manually changing the status back

7 Functional Flow: Branding & Localisation

Super AdminProperty Manager

Customise module names

Each condo can rename any module. Examples: "Facility Booking" → "Amenity Reservation", "Visitor Management" → "Guest Access", "Parcel" → "Delivery Locker". The custom name appears throughout the app for residents of that condo. All names support English and Chinese (zh-SG).

Customise role labels

Role display names can be changed per condo. "Staff" can become "Concierge", "Property Manager" can become "Building Manager". These labels appear in notifications and user-facing screens.

Set default language

Configure whether the condo defaults to English or Chinese (Simplified Singapore). Individual residents can override this in their profile settings, but the condo default is the starting language for all new users.

Configure home screen & menu order

Upload hero/banner images for the resident app's home screen. Drag-and-drop to set the display order of modules in the app's navigation menu. Modules can be completely hidden if the condo does not use them (e.g., hide "EAGM" if the condo doesn't use electronic AGM).

8 Functional Flow: Onboard a Property Manager

Super Admin

Receive PM details from the property management company

Collect: full name, email address, phone number, and which condo(s) they will manage. One PM can manage multiple condos.

Create the PM user account

In the User section, use the dedicated "Create PM" flow (not the general Create User). Set role_group = 5. Assign a temporary password — the PM should be asked to change it on first login.

Assign the PM to their condo(s)

Link the PM's user account to each condo they will manage. From this point, the PM can log into the backend and will see only their assigned condos — never other companies' data.

PM receives login credentials

Send the PM their backend login URL, username, and temporary password. The PM logs in, changes their password, and begins managing their condo(s). Super Admin's role in this process is now complete.

What a PM can and cannot do in the backend: A PM can configure condo settings, create and manage users within their condos, adjust wallet balances, and export reports. A PM cannot create new condos, create roles, set global permissions, or access condos they are not assigned to.

9 Functional Flow: Onboard Staff & Concierge

Super AdminProperty Manager

Determine the staff role

Decide which role the new staff member will have: General Staff (role_group=2), Concierge Admin (role_group=6), or iPlus Concierge Staff (role_group=7). Each role has different permissions pre-configured in the Permission setup.

Create the user account

Fill in: name, email, phone number, assign the correct role, assign to the correct condo. Set a temporary password. The staff member will use this to log into the frontend portal (not the backend).

Verify the permissions are correct for their role

Check that the module permissions for their assigned role match what they need. For example: A concierge staff should be able to add visitors and view facility bookings, but should not be able to approve/reject bookings or access financial settings. If permissions need adjusting, update the role's permissions (this affects all users of that role in this condo).

Staff logs into the frontend portal

The staff member receives their login URL (frontend portal, not backend) and credentials. They log in and see only the modules their role permits. Staff never access the backend admin panel.

Decision: What role should the new staff member get?
✅ Concierge AdminNeeds to approve visitors, manage parcels, handle bookings, coordinate access control
◆ General StaffNeeds read access to most things but limited write/approve abilities
⚙ iPlus Concierge StaffContracted concierge team from iPlus — specific operational access only

10 Functional Flow: Onboard a Resident

ResidentProperty ManagerSuper Admin

Resident downloads the iPlus Living app

The resident downloads the app from App Store or Google Play. The condo admin shares the app name/link with residents via welcome letter or email blast.

Resident self-registers

The resident enters their email, creates a password, and enters their unit number. The system verifies the unit number exists in the condo structure. On first login, if the condo has a tenancy agreement configured for residents, it is shown and must be accepted before proceeding.

Resident is linked to their unit

The system automatically creates the user-unit mapping in the user_condo table. Multiple residents can share the same unit (e.g., owner + spouse + children). Each gets their own account but shares the unit reference.

Alternative: Admin-created resident accounts
✅ Self-registrationStandard for most properties. Resident does it themselves via the app. Zero admin effort.
◆ Admin creationPM creates resident account manually in the backend. Used for elderly residents or when self-registration isn't working. PM sets a temporary password.
◆ Bulk pre-loadPM imports resident data via CSV before move-in day. Accounts are created and hidden until the resident activates them via email.

Upgrading a Resident to Council Member

When a resident is elected to the management council (MCST), a PM or Super Admin upgrades their role_group from 3 (Resident) to 1 (Council Member) in the backend. This immediately grants them access to council-specific features: voting, AGM management, financial reports, and council communications.

11 Functional Flow: Onboard Developer & Contractor

Super Admin
Context: This flow applies to new-launch properties where the building is still under construction. The property developer, main contractor, and sub-contractors need access to manage defect inspections, key collections, and handover activities.

Property Developer (role_group = 11)

  • Created by Super Admin via the dedicated "Create Developer" flow
  • Developer creates Developer Staff accounts (role_group=12) under their umbrella
  • Developer access: defect inspection management, key collection tracking, floor plan uploads, unit handover status
  • Cannot access resident personal data, facility bookings, or community features

Contractors (role_group 13–15)

  • Main Contractor (13): Manages rectification work
  • Main Contractor Staff (14): Field workers doing inspections
  • Sub Contractor (15): Specialist trades (plumbing, electrical)
  • Created via general Create User flow with appropriate role_group
  • Access limited to their assigned work orders and defect records

When Construction Completes

  • Super Admin marks the condo as construction-completed
  • Developer and contractor access is automatically reduced or removed
  • Resident features activate and residents can use the full app
  • All handover data (inspections, key collections, defects) is retained for historical reference

12 Functional Flow: Designing a Role

Super Admin
When to create a new role: The default role groups (Staff, Concierge Admin, etc.) cover most condos. Create a new role only when a specific type of user needs a distinctly different permission set that can't be achieved by adjusting an existing role's permissions.

Identify the need

A condo requests a "Security Supervisor" role that can approve vehicle registrations and view ANPR logs but cannot touch facility bookings or financial data. This is different enough from "Concierge Admin" that a new role makes sense.

Create the global role definition

In the Role section, create a new role: set its name in English and Chinese, assign a role_group (which tier it belongs to — this determines its base access level), pick a display colour, and set sort order. A UUID is auto-generated as the unique identifier.

Set default permissions for the role

Define what this role can do across all condos by default. These defaults can be overridden at the condo level later. Default permissions are useful when the same role is activated across many condos with the same behaviour.

Activate the role for the specific condo

Go to Condo Roles for the relevant property and link this new role. It now appears as an assignable role for users in that condo.

Set condo-specific permission overrides

Go to Role Permissions for this condo and configure exactly which modules this role can access in this specific property. These override the global defaults for this condo only.

Assign the role to users

Now create user accounts and assign this new role. The user immediately gets the permissions configured for this role in this condo.

14 Functional Flow: Changing Permissions

Super Admin

Identify the need

Example: The condo requests that concierge staff should no longer be able to cancel bookings — only the Property Manager should have that ability.

Go to Role Permissions for the specific condo

Navigate to the condo, then to Role Permissions. Find the "Concierge Admin" role and locate the "Facility Booking" module permissions.

Update the permission flag

Uncheck the "Delete" permission (which controls cancellation in this context). Save the changes. The system immediately clears all relevant caches.

Effect is immediate

All users with the Concierge Admin role in this condo lose the cancel booking ability on their next page load. They do not need to log out and back in — the cache invalidation is instant. Users currently logged in will see the change on their next page navigation.

Important: Permissions are role-level, not user-level. Changing a permission for a role affects ALL users with that role in that condo simultaneously. If you need to give one specific user different permissions from their colleagues, you need to either create a new role just for them or use individual permission overrides via UserinfoController.

16 Functional Flow: Payment Configuration

Super AdminProperty Manager

Choose the payment gateway

In Condo Settings, set the payment_type. Options: Stripe (credit/debit cards, international), BrainTree (PayPal and cards), PayLah (Singapore DBS wallet), Manual (cash/bank transfer, no online processing), Wallet (iPlus in-app wallet only). Only one gateway is active at a time per condo.

Decide who bears the payment processing fee

For Stripe: enable or disable "Condo Bears Stripe Handling Fee". If enabled, the condo absorbs the Stripe processing percentage. If disabled, the handling fee is added on top of what the resident pays. This affects the amount shown to residents at checkout.

Configure manual payment instructions (if applicable)

If Manual Payment is allowed as an option on any facility: set the customise_manual_payment label (e.g., rename "Manual Payment" to "Bank Transfer") and configure the payment instructions text shown to residents (menual_payment_message).

Configure wallet settings (if using in-app wallet)

Set minimum top-up amounts, maximum balance limits, and whether wallet can be used alongside other payment methods or is the sole method.

17 Functional Flow: House Rules & Tenancy Agreement

Super AdminProperty Manager

Prepare the house rules document

The property management company provides the house rules or tenancy agreement as a PDF or formatted HTML. This document is what residents must agree to before using the app.

Configure which roles must accept the agreement

In Condo Roles, for each role, configure the activation permission: "Must Accept Agreement = Yes/No". Typically residents (role_group=3) must accept; staff (role_group=2) usually do not. Council members may or may not depending on condo policy.

Upload the agreement document

Link the agreement document to the condo. The agreement is shown in-app as a scrollable document. The resident must scroll to the bottom and tap "I Agree" before they can proceed to use the app.

When the agreement is updated

If house rules change: upload the new version of the document. The system detects a new version and forces all applicable users to re-accept on their next login — even if they accepted the previous version. Their acceptance is tracked individually.

18 Functional Flow: Module Behaviour Configuration

Super AdminProperty Manager

Facility Booking Behaviour

  • Auto-approve: Toggle whether bookings need staff approval or are confirmed instantly
  • Booking note label: Rename the "Booking Notes" field to something condo-specific
  • Cancellation message: Set the message shown when a resident tries to cancel a past-due booking
  • Manual payment label: Rename "Manual Payment" to match how the condo collects offline payments

ANPR / Vehicle Behaviour

  • Overstay threshold: Minutes after which a parked vehicle is flagged as overstaying (set per camera)
  • Operating hours: Time window within which overstay detection runs
  • Face enrollment: Enable/disable Hikvision face ID enrollment for residents
  • Camera credentials: IP, port, username, password for each ANPR camera

Authentication Behaviour

  • OTP / 2FA: Enable one-time password requirement on login
  • Session timeout: Auto-logout after X minutes of inactivity
  • Force password reset: Make specific role groups reset their password on next login
  • Password complexity: Set minimum length and character requirements

Communication Behaviour

  • Email server: Configure SMTP settings for condo-specific email sending
  • Notification preferences: Which events trigger push notifications to which roles
  • SFTP: Set up file sync for document exchange with external systems
  • Language: Default language for all system-generated messages

19 Functional Flow: Bulk Data Operations

Super AdminProperty Manager

Download the CSV template

From the Condo section, download the blank CSV template for the type of data to be imported (units, vehicles, inspections, etc.). Templates define the exact column headers and format required.

Fill in the data

Populate the CSV with the data. Common pitfalls: date formats (use the format shown in the template), unit names must match exactly what is in the system, vehicle plate numbers must be in the correct format without spaces.

Upload and process

Upload the CSV via the import action for that data type. The system validates the file (MIME type check — only CSV/Excel formats accepted). Rows with missing required fields are skipped. The system returns a success count and a list of skipped rows with reasons.

Verify imported data

After import, navigate to the relevant section (units list, vehicle list, etc.) and confirm the data has been loaded correctly. Spot-check a few records for accuracy before notifying the client that setup is complete.

What CAN be bulk imported

  • Units (block, floor, unit name, unit type)
  • Unit purchase details (price, buyer, owner)
  • Unit QR codes
  • Resident vehicles (plate, IU, vehicle type)
  • Inspection / defect checklist templates
  • Notification and document templates

What CANNOT be bulk imported

  • User accounts / resident registrations (must self-register or be created individually)
  • Role and permission definitions (manual configuration only)
  • Payment transactions (cannot be bulk-injected)
  • ANPR parking logs (received from hardware in real-time only)

21 Functional Flow: Wallet Management

Super AdminProperty Manager

Resident reports a wallet issue

Common situations: payment was made but wallet was not credited, a failed top-up deducted money but didn't add balance, or a refund should be issued as wallet credit.

PM investigates the transaction history

Use the wallet balance export or payment process export to see the transaction history for the affected user and identify the discrepancy.

Adjust the wallet balance manually

In the user's account settings (backend), PM or Super Admin uses the "Change User Balance" function to add or subtract the correct amount. A reason/note should be recorded. The change is logged as a transaction for audit trail.

Notify the resident

The system automatically sends a wallet update notification to the resident's device. PM may also follow up directly to confirm the issue is resolved.

22 Key Business Rules Summary

Condo Rules

  • A condo must have at least one Property Manager assigned before residents can be served effectively
  • Condo status determines what is accessible — Under Construction blocks resident features
  • Subscription dates define the licence window — expired condos lose access to the platform
  • All condo settings can be changed at any time without affecting historical data

User Rules

  • Every user must be assigned to at least one condo to have any functional access
  • A user can be assigned to multiple condos (e.g., a PM managing 5 properties)
  • Deleting a user is a soft delete — data is retained, access is revoked
  • A resident can share a unit with other users — unit has many users, user can belong to one unit per condo

Role & Permission Rules

  • Global roles must be activated per condo before users can be assigned that role in that condo
  • Permissions are role-level, not user-level — changing a role affects all users of that role
  • Condo-level permissions override global role defaults
  • Permission changes take effect on the user's next page load — no logout required

Payment Rules

  • Only one payment gateway is active per condo at any time
  • Changing the payment gateway does not affect historical transactions
  • Manual payment mode requires staff to manually confirm receipt — it is not automated
  • Wallet balance is tracked per user per condo — the same user in two condos has two separate balances

Data Rules

  • Sensitive data (email, phone, plate numbers) is AES-encrypted in the database
  • All admin user credentials (super admin panel accounts) are separately encrypted in the adminuser table
  • Role changes are always audit-logged in iliving_sync_data — creation, updates, and deletes
  • CSV imports skip invalid rows silently — always verify imported data after upload

Irreversible Actions

  • "Mark Construction Completed" — cannot be undone without manual status change by Super Admin
  • Subscription end date passing — condo access is cut off; must be manually renewed
  • Wallet balance adjustments — manually logged, no automated rollback
  • Permission cache cleared on every role save — cannot be selectively cleared for one user

23 Decision Trees

Decision: Who should create this user account?

Identify the user type being created
✅ Property ManagerSuper Admin must create this — PMs cannot create other PMs
◆ Staff / ConciergePM or Super Admin can create this in the backend
◆ ResidentResident self-registers via app, OR PM creates manually, OR bulk import
⚙ Developer / ContractorSuper Admin must create — requires role_groups 11–15

Decision: Should I create a new role or adjust an existing role's permissions?

Ask: Is this user genuinely different from ALL existing role types?
✅ Yes — Create new roleThe user needs a unique combination of permissions that no existing role has. Example: "Security Supervisor" needs ANPR access but not booking management.
❌ No — Adjust permissionsAn existing role is close enough. Go to Role Permissions for the condo and tweak the permission flags for that role. Faster and simpler.

Decision: What to do when a staff member leaves?

Will this user's account ever be needed again?
Permanent departureForce Disable the account. Data is preserved for audit history. Account cannot be used to log in. If the account will never be reactivated, you may also change the email to a placeholder so the email can be reused for a new hire.
Temporary (leave of absence)Force Disable the account. When the employee returns, Force Enable to restore access. No data is lost, permissions remain intact.

Decision: Resident cannot self-register — what is the problem?

What error is the resident seeing?
"Unit not found"Unit name mismatch. Check how the unit is stored in the system vs what the resident typed. May be a format issue (#01-01 vs 01-01).
"Email already registered"Someone already registered with that email. Check if the account exists and if it's linked to the correct unit.
App not loadingMay be a condo status issue — check if the condo is set to "Under Construction" which blocks resident app access.
Agreement not appearingCheck if tenancy agreement is configured for the resident role in Condo Roles. If not configured, the agreement step is skipped.
