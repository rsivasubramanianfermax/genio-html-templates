EEP · OPC Architecture

OPC Barrier Control
Architecture Document

How the Operation PC (OPC) service collects OBU data from the EEP DSRC Device, validates it, and opens the barrier — without payment processing.

Scope of this document: The OPC service connects to the EEP DSRC Device over Ethernet (TCP/IP), receives OBU data when a vehicle arrives, validates it, and sends a command to open the barrier. Payment processing (NETS Cashcard, CEPAS, BE-Pay) is out of scope.

System Components

External

EEP DSRC Device

Communicates with OBU via DSRC. Sends OBU data to OPC over Ethernet. Controls barrier via DIO port.

On-Site PC

OPC Service (this)

TCP client that receives EEP messages, validates OBU info, and sends barrier open command back to EEP device.

Hardware

Barrier Gate

Connected to EEP DSRC Device via Digital Output (DO) port. OPC triggers it indirectly via Set DO Request.

Hardware

Loop Coil

Detects vehicle presence. Connected to EEP DSRC Device's DI port. Triggers DSRC communication sequence.

Optional

Terminal Station (TS)

Per-lane device for LED display, receipt printing, and handling vehicles without OBU. Not in scope for this flow.

Optional

iplus Backend API

OPC can call the iplus-living backend to validate whether a vehicle's OBU is registered/authorized.

EEP Device
1
→ OPC DI Status Notification Loop coil ON — vehicle at exit lane
EEP Device
2

EEP Device
3
→ OPC OBU Information Notification Same OBU fields; entry/exit flag = EXIT
OPC
4

OPC

OPC

⚠️

Timing constraint: OPC must send Carpark Process Complete Notification to the EEP device after the barrier open command (Set DO Request), and only after completing its own processing. If OPC delays, the EEP device will time out the DSRC session.

IU Label is non-null and non-empty		 Continue Log error, keep barrier closed, send error display to OBU
2 IU Label format valid
Matches expected format from interface spec		 Continue Log error, keep barrier closed

💡

Validation source options: (1) Local DB on OPC machine — fastest, works offline; (2) iplus-living backend API — always up to date, requires LAN/internet connectivity. Recommended approach: primary check against local DB synced from iplus backend, with fallback to API for real-time lookups.

Section 5

OPC Service — Internal Architecture

Layer 1

TCP Connection Manager

Maintains persistent TCP socket to EEP DSRC Device. Auto-reconnects on drop. One connection per lane/device.

Layer 2

Protocol Parser / Encoder

Reads raw bytes from TCP stream, decodes them into message objects per CTR150/EIS/OPC(SI) interface spec. Encodes outbound messages to bytes.

Layer 3

Message Dispatcher

Routes inbound messages to handlers based on command ID. Stateful: tracks current vehicle session per lane.

Layer 4

OBU Validator

Validates IU Label and Vehicle Number. Queries local vehicle registry or iplus-living API. Returns pass/deny with reason.

Layer 5

Barrier Controller

Builds and sends Set DO Request message to EEP device to trigger barrier open via DO port. Follows with Carpark Process Complete Notification.

Layer 6

Session & Audit Logger

Logs each vehicle session (IU Label, Vehicle Number, entry/exit time, validation result, barrier action) to local DB or API.

Key Message Handlers OPC Must Implement

Message (Inbound from EEP) OPC Action
DI Status Notification (Loop ON) Begin vehicle session. Start timeout timer. Log lane activity.
OBU Information Notification Extract IU Label, Vehicle Number, VCC, entry/exit flag. Run validation. Decide barrier action.
Additional OBU Information Supplement session data if needed. (May not be needed for non-payment flow.)
DSRC Process Complete Notification End session. Log completion. Release lane for next vehicle.
DI Status Notification (Loop OFF) Confirm vehicle has cleared the lane. Close session record.
Message (Outbound from OPC) When Sent
Set DO Request After validation passes — tells EEP device to activate barrier DO port (open gate).
Carpark Process Complete Notification After barrier command — signals to EEP device that OPC-side work is done.
CPO/EEP Information Display Request Optional — send welcome / denied message to display on OBU screen.
Get OBU Information Stop If OPC needs to abort the DSRC session (e.g., manual override).
Section 6

Protocol Layer — What You Need from the Interface Spec

The EEP manual references CTR150/EIS/OPC(SI) — Interface Specification between OPC/TS and EEP DSRC Device (For Carpark SI). This is the document that defines the actual TCP message format. Before implementing the protocol parser/encoder, the following must be obtained from it:

Item Needed Why
TCP port number of EEP DSRC Device OPC initiates TCP connection to EEP device — needs the port
Message frame format
(header, length field, command ID, payload, checksum)		 To correctly parse incoming bytes and encode outgoing messages
Command ID table
(hex code per message type)		 To route inbound messages to correct handler in dispatcher
OBU Information Notification payload layout Field offsets/sizes for IU Label, Vehicle Number, VCC, entry/exit flag
Set DO Request payload layout Which DO port number maps to the barrier; open vs. close values
Carpark Process Complete Notification payload Required fields (lane ID, result code, etc.)
Timeout values How long EEP device waits for OPC response before timing out
⚠️

Design tip: Isolate all byte-level encoding/decoding in a single EepProtocol module. The rest of the OPC service (validation, barrier control, session management) should operate on typed message objects, not raw bytes. This way, the protocol implementation can be filled in once you have the interface spec without touching business logic.

Section 7

Error & Edge Case Handling

Scenario What Happens OPC Behaviour
OBU not present (vehicle has no OBU) EEP device reports DSRC failure after timeout OPC receives DI On but no OBU Notification → hand off to Terminal Station (TS) for manual handling
Vehicle not in authorized list Validation returns deny OPC does NOT send Set DO Request. Optionally sends CPO/EEP Display Request with "Not Authorized" message. Logs the attempt.
TCP connection to EEP device drops Socket closed / timeout Auto-reconnect with exponential backoff. Log disconnection. Barrier stays in last state (closed by default on EEP side).
Validation API unreachable (iplus backend down) HTTP timeout / error Fallback to local DB. If local DB also unavailable, apply configurable policy: deny all OR allow all with alert.
OPC crashes mid-session No Carpark Process Complete sent EEP device will timeout its own DSRC session. On OPC restart, reconcile open sessions from DB. Barrier should be fail-safe (closed).
Duplicate OBU notification Same vehicle triggers twice (bouncing loop coil) OPC checks if a session is already active for that IU Label → ignore duplicate within cooldown window (e.g., 10s)

Appendix A

What is Season Parking?

Season Parking is a monthly/periodic parking subscription — a vehicle pays a fixed flat fee (monthly or quarterly) to park at a specific car park, rather than paying per entry/exit trip. It is the primary access control model this OPC is built for.

TypeHow It WorksCharge
Hourly Parking Pay based on duration of each parking session Per trip (duration-based)
Season Parking Pre-paid subscription — unlimited entry/exit during valid period Flat monthly/quarterly fee
Complimentary Free parking — mall validation, visitor pass, staff, disability No charge
💡

In this OPC system, the registered vehicle list = season parking holders (plus staff / complimentary vehicles). The OPC checks if the arriving vehicle is an active, non-expired season parker and opens the barrier. No per-trip fee calculation is needed — which is why payment processing is out of scope.

Season Parking Lifecycle in iplus + OPC

  • 1
    Resident applies for season parking in iplusSubmits vehicle number, IU Label, desired period
  • 2
    Admin approves and sets valid_untile.g., valid_until = 2025-01-31 (end of month)
  • 3
    iplus syncs record to OPC local DBVia delta sync — OPC receives new/updated record
  • 4
    Vehicle arrives at barrierEEP DSRC Device reads OBU → sends OBU Information Notification to OPC
  • 5
    OPC checks: status = active AND valid_until ≥ today?YES → barrier opens · NO → barrier stays closed (expired or not renewed)
  • 6
    On expiry — resident must renew in iplusiplus updates valid_until → OPC syncs → barrier works again

Appendix C

Local Vehicle Registration on OPC

The OPC operator can register new vehicles directly on the OPC machine — not just rely on iplus backend sync. When added locally, the record is saved to the local DB immediately (barrier works right away) and pushed to iplus in the background.

Registration Form Fields (OPC UI)

FieldInput TypeRequired
IU LabelText input / barcode scanRequired
Vehicle NumberText input (license plate)Required
Resident / UnitDropdown (from synced unit list)Required
Valid UntilDate pickerRequired
Access ZoneMulti-select (which barriers)Required
Vehicle Type / VCCDropdown (Car / Motorcycle / Heavy)Optional
NotesText areaOptional

Registration Flow

  • 1
    Operator fills in registration form on OPC UIIU Label, vehicle number, unit, valid until, access zone
  • 2
    OPC saves to local SQLite immediatelystatus = active, source = opc, synced_to_backend = false — barrier works right away
  • 3
    Background job: POST /api/vehicles to iplus backendPushes new registration up to master DB
  • 4
    On success: mark record as synced_to_backend = trueiplus now has the record as master; will sync to all other OPCs on next delta
  • 5
    On failure: add to retry queueRetry every 1 minute. Alert operator after 10 failed attempts.
⚠️

Offline support: If the OPC machine has no internet/LAN at the time of registration, the vehicle is still registered locally and can use the barrier immediately. The record syncs to iplus as soon as connectivity is restored via the retry queue.

Conflict Handling

ScenarioResolution
Same IU Label registered on OPC and iplus simultaneously iplus backend is master — last write wins. OPC gets corrected on next delta sync.
OPC registered a vehicle while offline; iplus already has it Backend returns 409 Conflict → OPC merges / updates local record with backend version.
Vehicle deleted/suspended on iplus while OPC is offline On next delta sync, OPC receives status = suspended / deleted → updates local DB → barrier blocks.

Message Framing — How Raw Bytes Become Messages

TCP is a byte stream with no concept of "messages." The EEP protocol uses a frame structure to mark where each message starts and ends. The typical structure for such systems:

└─────────┴──────────┴───────────┴───────────┴─────────────────┴──────────┘
⚠️

Important: The exact byte offsets, field sizes, and checksum algorithm are defined in CTR150/EIS/OPC(SI). The above is a typical pattern — always verify against the actual interface spec before implementing the parser.

How OPC Listens to the TCP Socket

Node.js uses an event-driven model. You register callback functions once — Node.js watches the socket in the background and fires them automatically when data arrives. You never write a manual polling loop.

Step 1 — Open the Connection (once on startup)

import * as net from 'net';

const socket = new net.Socket();

// Connect to EEP DSRC Device — IP + port from config
socket.connect(8080, '192.168.1.100', () => {
  console.log('Connected to EEP DSRC Device');
  // Connection stays open — do NOT close it
});

Step 2 — Listen for Incoming Data

// This fires AUTOMATICALLY whenever EEP sends anything
// You register it ONCE — Node.js handles the rest
socket.on('data', (chunk: Buffer) => {
  // chunk = raw bytes that just arrived from EEP device
  processBytes(chunk);
});
💡

socket.on('data', ...) is the listener. Node.js runs an event loop that watches the socket 24/7. The moment EEP sends anything — vehicle arrives, OBU connects, barrier confirmed — your callback fires automatically. No need to keep asking "did anything come in?"

Step 3 — Buffer Bytes Into Complete Messages

TCP is a stream — one EEP message may arrive split across 2 chunks, or 2 messages may arrive in 1 chunk. You must buffer bytes until you have a complete frame:

let buffer = Buffer.alloc(0);
const HEADER_SIZE = 5; // STX + CmdID + SeqNo + Length(2)

socket.on('data', (chunk: Buffer) => {

  // ① Add new bytes to running buffer
  buffer = Buffer.concat([buffer, chunk]);

  // ② Extract complete messages in a loop
  while (true) {

    // Not enough bytes for a header yet — wait for more
    if (buffer.length < HEADER_SIZE) break;

    // Read payload length from header (bytes 3-4)
    const payloadLength = buffer.readUInt16BE(3);
    const totalSize     = HEADER_SIZE + payloadLength + 1; // +1 checksum

    // Full frame hasn't arrived yet — wait for more chunks
    if (buffer.length < totalSize) break;

    // ③ Extract one complete frame
    const frame = buffer.slice(0, totalSize);
    buffer      = buffer.slice(totalSize); // remove it from buffer

    // ④ Route to correct handler
    handleMessage(frame);
  }
});

Step 4 — Route & Handle the Message

function handleMessage(frame: Buffer) {
  const commandId = frame.readUInt8(1); // byte 1 = command ID

  switch (commandId) {
    case 0x01: handleLoopCoil(frame);    break; // DI Status Notification
    case 0x02: handleObuArrival(frame);  break; // OBU Information Notification
    case 0x04: handleSessionDone(frame); break; // DSRC Process Complete
    case 0x11: handleSetDoResponse(frame);break; // Set DO Response
  }
}

async function handleObuArrival(frame: Buffer) {
  // Extract OBU fields from payload
  const iuLabel       = frame.slice(5, 15).toString('ascii');
  const vehicleNumber = frame.slice(15, 25).toString('ascii');

  // Validate against local DB
  const isValid = await validator.check(iuLabel);

  if (isValid) {
    socket.write(encodeSetDoRequest()); // send barrier open command
  }
}

socket.on('close', () => {

socket.on('error', (err) => {

function reconnect(attempt = 1) {
  const delay = Math.min(1000 * attempt, 30000); // max 30s between retries
  setTimeout(() => {
    socket.connect(8080, '192.168.1.100', () => {

Appendix K

How Does the EEP DSRC Device Know Where to Send Data?

The Short Answer

💡

The EEP DSRC Device does NOT need to know your OPC app's IP address. When your OPC app connects to the EEP device, TCP automatically creates a two-way pipe. The EEP device sends data back through that exact same pipe — no separate outbound connection needed.

The Phone Call Analogy

HTTP  = Sending a letter.
        You write it, post it, wait for a reply.
        The other person can ONLY respond to YOUR letters.
        They cannot write to you first.

TCP Socket = A phone call.
        You dial the number (OPC connects to EEP's IP + port).
        They pick up (EEP accepts the connection).
        Now BOTH can talk freely through the same open line.
        They don't need to "dial back" — the line is already open.

What Actually Happens — Step by Step

  • 1
    OPC app starts — knows EEP device IP + port (from config) EEP_IP = 192.168.1.100 · EEP_PORT = 8080 — set once in settings
  • 2
    OPC calls socket.connect('192.168.1.100', 8080) OPC dials the EEP device — only OPC needs to know the address
  • 3
    TCP 3-way handshake completes OPC → SYN → EEP · OPC ← SYN-ACK ← EEP · OPC → ACK → EEP
  • 4
    EEP device now holds a reference to this connection EEP can see: "OPC connected from 192.168.1.50 port 54321" — it stores this socket
  • 5
    Vehicle arrives → EEP sends data through the SAME connection EEP writes bytes into the existing socket → arrives at OPC's socket.on('data') handler
  • 6
    Connection stays open until OPC or EEP closes it No reconnect needed between vehicles — same pipe used for all events all day

What Each Side Needs to Know

OPC App (your code) needs:

  • EEP device IP address (e.g., 192.168.1.100)
  • EEP device TCP port (e.g., 8080)
  • Nothing else — OPC initiates everything

EEP DSRC Device needs:

  • Its own port to listen on (8080)
  • Nothing about OPC's IP address
  • Just accepts whoever connects and uses that socket to reply

EEP_IP   = 192.168.1.100          (nothing about OPC)
EEP_PORT = 8080                   LISTEN_PORT = 8080

Inside EEP Device Firmware (Conceptual)

To help visualise — this is what the EEP device firmware does internally (concept only, not actual code):

// EEP device firmware — simplified concept
server.listen(8080);

server.on('connection', (opcSocket) => {
  // opcSocket = the connection YOUR OPC app opened
  // EEP stores this reference — no need to know OPC's IP

  loopCoil.on('vehicleDetected', () => {
    opcSocket.write(diStatusNotification); // sends back on SAME pipe
  });

  obu.on('dataReady', (obuData) => {
    opcSocket.write(obuInfoNotification);  // same pipe again
  });

💡

Your OPC code does the same thing in reverse — your socket.on('data') is the equivalent of EEP's opcSocket.on('data'). Both sides are just listening on the same open pipe and writing to it when needed.

What Happens if OPC Restarts?

  • 1
    OPC crashes or restartsTCP connection drops — EEP device detects socket closed
  • 2
    EEP device discards the old socket referenceIt goes back to waiting for a new connection on port 8080
  • 3
    OPC restarts — calls socket.connect() againNew TCP connection established — new socket reference on both sides
  • 4
    Communication resumes normallyEEP device now sends all events through the new pipe

During the disconnection window, vehicles arriving at the lane will trigger the EEP device but OPC won't receive the notifications. This is why the auto-reconnect logic (Appendix J, Step 5) must reconnect as fast as possible — ideally within 1–2 seconds.
