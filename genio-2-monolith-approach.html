Bounded Context Architecture

Two monoliths, ~20 bounded contexts distributed between them. The monolith count is a deployment decision; the bounded-context count is a modeling decision — each context keeps its own schema, rules, and vocabulary regardless of which monolith it deploys inside.

System Architecture — Monoliths, Service Bus, and Shared Database

One physical database serves both monoliths — no split by service. Inter-monolith traffic never touches the external Gateway; it stays on the internal network via a direct sync API call or an async Service Bus event, depending on the pattern.

What keeps this from becoming legacy system #2

  • No context reaches directly into another's tables or repository. Every cross-context interaction goes through a defined interface — an event or an internal API — the same discipline applies whether the two contexts share a process (inside Monolith 1) or cross a network boundary (Monolith 1 ↔ Monolith 2).
  • Vendor integrations each get their own anti-corruption layer. Hikvision, EPS, VIDA, and IP Camera each translate their own vendor-specific data shape into ME's internal model — vendor quirks never leak into the core domain or into each other.
  • The holiday/holiday_by_days/non_working_days tables are a deliberate shared kernel — reused as-is by Facilities, ME, Handover, and Smart Home Gateway, rather than each context reimplementing its own calendar.
  • Clean boundaries today make extraction cheap later. If Payments (or any other Monolith 1 context) later proves it needs independent scaling, extracting it means turning an in-process call into a network call — not untangling years of direct cross-references, because the boundary already exists in the code.
